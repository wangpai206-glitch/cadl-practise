### 演讲者备注

We first introduce the challenges in ASIP hardware synthesis. Since the emergence of ASIPs, there have been several approaches to customizing ISAXs.

First, the traditional RTL-based approach: Verilog is the most commonly used and fundamental RTL language. In recent years, more agile RTL languages and platforms, such as Chisel and Chipyard, have also appeared. However, they are still confined to the RTL development approach and require developers to have deep hardware expertise, resulting in the low agility.

Second, some commercial tools, such as GlobalFoundries ASIP Designer Codasip and so on. These tools typically allow users to describe ISAXs using higher-level languages and automatically generate Verilog. They offer relatively high development efficiency and rich features, but are often not open source and extensible

Third, some academic works, such as SCAIE-V and Longnail. They also describe ISAX using high-level languages and automatically generate Verilog, but their functionality is relatively limited, making them difficult to use for designing complex and highly optimized ISAXs.

We proposed APS, aim to provide an open-source, agile, and optimized hardware synthesis approach for ISAXs.

### 演讲者备注

We now introduce the APS hardware synthesis flow. The entire flow starts from CADL, which is a high-level ISAX description language designed by us. Next, we parse CADL into unoptimized MLIR. Both of these are untimed representations of ISAXs. Then, APS performs a series of optimization transformations on MLIR and assigns timing information to the IR through high-level synthesis scheduling. During this process, the IR follows software-like semantics, leveraging many standard dialects provided by MLIR as well as our APS dialect. Next, APS transforms the scheduled MLIR into purely hardware semantics, using the FIRRTL and CMT2 dialects. Finally, APS uses FIRRTL and CMT2 to generate Verilog.

### 演讲者备注

Before introducing CADL, I would like to explain why we need to design our own language to describe ISAXs, instead of reusing existing ADLs or high-level software languages.

In ASIPs, different types of general-purpose processors can be used as base processors, each with different microarchitectural designs, such as pipeline stages and memory interfaces. ISAXs can also be implemented in various ways, including custom function units, custom coprocessors, and dedicated accelerators, which differ significantly in how they communicate with the CPU core. Even for the same type of ISAX implementation, there can be different ISAX interfaces, such as RoCC and CV-X-IF, imposing different constraints on ISAX behavior. Therefore, we believe that a unified abstraction of the processor–ISAX interface is needed.

### 演讲者备注

Therefore, we propose APS-itfc, which is a transactional processor–ISAX abstraction. APS-itfc abstracts the interface between the processor and the ISAX as a set of transactions, including issue requests to issue a new instruction; GPR requests to receive source operands; read/write memory requests to request a single memory access; read/write memory response to receive a single memory access; read/write block memory request to request a block memory access; read/write block memory response to receive a block memory access; result response to send the final results to the core.

### 演讲者备注

First, we briefly introduce MLIR. MLIR is a compiler infrastructure that makes it very convenient for users to define custom IRs and transformations. MLIR also provides many standard IRs. This is the generic representation of an MLIR operation, which is the basic syntax of MLIR. MLIR is an SSA-based IR, where each operation has results. Each operation is prefixed with a dialect. Dialects are first-class citizens in MLIR, and defining new dialects is a way for users to extend the IR. An operation has operands and attributes; attributes can be viewed as constant parameters. Finally, operations have types, which can include both user-defined dialect-specific types and standard types. MLIR is widely used in recent compilers, such as PyTorch, Triton, and CIRCT.

### 演讲者备注

After the optimization transformations, we perform HLS scheduling to assign timing information to each operation. Our scheduling is based on modeling the problem as a system of difference constraints. The constraints in the SDC come from data dependencies, resource constraints,  timing constraints and so on. The SDC represents all constraints as difference constraints, where each constraint corresponds to an edge in a graph. For example, in the hello.cadl, addi depends on readrf and must start one cycle after readrf, so there is an edge from readrf to addi with weight 1. Since writerf depends on addi, but addi can complete within one clock cycle, writerf can start in the same cycle as addi, so there is an edge from addi to writerf with weight 0. Our SDC solver computes the longest paths in the SDC graph to determine the start time and end time of each operation. Please see tutorial/outputs/hello/1_hello_scheduled.mlir, where we attach timing information to operations as attributes. Note that the tor dialect appears here, because we modified the MLIR-based HLS tool Hector to implement our ISAX-specific scheduling.
